# 河道漂浮物识别与处置闭环系统（MVP）

当前版本提供一条可直接演示的单类漂浮物处置闭环：

`图片/摄像头/RTSP → 抽帧检测漂浮物 → 自动预警与建议 → 人工清理 → 上传复核图片 → 未发现漂浮物后归档事件`

暂不识别水质污染、废弃船只和捕鱼养殖设施，也不包含地图、GPS、消息通知和多模态传感器。

## 系统使用流程

### 1. 登录并进入系统

启动服务后，在浏览器打开电脑端首页或移动端页面。启用登录保护时，系统会先显示登录页；使用部署人员在 `.env.server` 中配置的管理员账号和密码登录。登录仅在当前浏览器会话内有效，关闭浏览器后再次访问需要重新登录。

- 电脑端：`http://127.0.0.1:8000/`
- 移动端：`http://127.0.0.1:8000/mobile/`
- 公网访问：使用部署完成后提供的 HTTPS 地址；移动端调用浏览器摄像头必须使用 HTTPS。

首次在手机使用时，建议直接用浏览器打开 `/mobile/`，允许相机权限。图片选择按钮同时支持拍照和从相册选择图片。

### 2. 现场巡护与识别

1. 进入“图片识别”或移动端“现场巡查”。
2. 拍摄/选择河道图片，填写河段名称；河段名称可自定义填写。
3. 点击识别，系统以 `river_floater.pt` 检测图片中的 `floater` 漂浮物。
4. 页面展示原图、检测框图、漂浮物数量、最高置信度和预警结果；识别图片会保存在检测记录中。

预警仅按识别出的漂浮物数量确定：1～3 个为黄色预警，4～7 个为橙色预警，8 个及以上为红色预警；未识别到漂浮物时不创建预警事件。

### 3. 自动生成并查看事件

识别到漂浮物后，系统自动创建事件台账，标题会包含河段名称和实际漂浮物数量。进入“事件台账”可：

- 按状态筛选事件；“已归档”表示已关闭的历史事件；
- 查看现场原图、检测框图、处理记录和复核图片；
- 删除误建或不再需要的事件。删除事件不会删除原始检测记录和证据图片。

### 4. 事件处置闭环

事件必须按以下顺序流转：

```text
待确认 → 已派单 → 处理中 → 已处理 → 复核通过 → 已归档
```

1. **已派单**：填写处理人员。
2. **处理中**：开始现场打捞、清理或处置。
3. **已处理**：填写清理说明，例如清理范围、数量或完成情况。
4. **上传复核图片**：在事件详情选择清理后的图片并提交复核。
5. **确认复核通过**：只有复核图片未检测到漂浮物时，才可进入“复核通过”。
6. **归档**：将已复核通过的事件关闭归档。

移动端事件详情会显示复核结论（通过/未通过）、复核风险等级、置信度、复核时间及对应图片。若复核仍发现漂浮物，应继续清理后重新上传复核图片。

### 5. 摄像头巡护（可选）

- **浏览器摄像头**：在电脑端“摄像头巡护”打开浏览器摄像头，系统会按间隔上传画面分析。公网手机访问必须通过 HTTPS，否则浏览器会禁止调用摄像头。
- **OpenCV / RTSP**：填写 USB 摄像头编号、视频文件路径或 RTSP 地址，由服务器持续抽帧巡护。该模式即使关闭网页也会继续运行，但摄像头必须能被服务器访问。

为降低误报，视频巡护通常要求连续两帧检测到漂浮物才新建普通事件；同一河段已有未归档事件时，系统会复用该事件而不重复建单。

### 6. 日常维护

- 登录账号、密码和会话密钥只保存在服务器 `/opt/river-patrol/.env.server`，不要写入代码、README 或部署包。
- 业务数据库和上传图片位于服务器 `/opt/river-patrol/runtime/`，升级前先备份该目录。
- 更换模型时更新 `weights/river_floater.pt` 或 `.env.server` 的 `RIVER_MODEL`，再重新构建并部署容器。
- 服务健康检查：`curl http://127.0.0.1/health`；查看容器：`docker compose -f compose.ip.yaml ps`。

## 当前模型

- 权重：`weights/river_floater.pt`
- 类型：Ultralytics YOLOv8 目标检测
- 类别：`floater`，系统统一显示为“漂浮物”
- 默认检测阈值：0.3
- 来源：[esapzoi/litter-detection-yolov8](https://huggingface.co/esapzoi/litter-detection-yolov8)

该权重用于识别河道漂浮物，适合课程设计和 MVP 演示。正式部署前仍应使用真实河道图片完成评测。

## 移动端 PWA

服务启动后，访问 <http://127.0.0.1:8000/mobile/> 可打开移动端巡护页面，支持：

- 手机拍照或从相册上传图片识别漂浮物；
- 查看、筛选、派单、处理、复核、归档和删除预警事件；
- 在“连接设置”中配置服务地址。

手机与服务端处于同一局域网时，请将 `127.0.0.1` 替换为部署电脑的局域网 IP，例如：

```text
http://192.168.1.10:8000/mobile/
```

页面可在手机浏览器中使用。若要使用“安装应用/添加到主屏幕”的完整 PWA 能力，生产部署需要配置 HTTPS；局域网 HTTP 环境下不影响页面和接口功能。

公网服务器部署请参阅 [deploy/README.md](deploy/README.md)。该方案使用 Docker 和 Caddy 自动配置 HTTPS，部署完成后可从任意网络访问移动端。

## 摄像头视频巡护

管理页面提供两种模式：

- 浏览器摄像头：适合本机或 USB 摄像头演示。浏览器显示实时画面并按 5～15 秒间隔上传一帧。
- OpenCV / RTSP：后端直接连接 USB 设备编号、视频文件或 RTSP/IP 摄像头。推理线程在服务端运行，关闭网页后仍会继续巡护。

视频预警采用以下规则：

- 连续两帧发现漂浮物才创建普通事件，降低水面反光造成的误报。
- 3 级“大量漂浮物”第一帧即可创建事件。
- 同一河段已有未关闭事件时复用原事件，不重复派单。
- RTSP 中断后 OpenCV 使用 TCP 自动尝试重连。

网页中选择“OpenCV / RTSP”，视频源可以填写：

```text
0
rtsp://用户名:密码@摄像头IP:554/视频路径
```

`0` 表示后端主机上的第一个 USB 摄像头。

## RTSP 无人值守部署

不要把摄像头密码写进代码。部署主机打开 Miniconda Prompt 或 PowerShell，设置环境变量后启动：

```powershell
cd 'C:/Users/20346/Downloads/河道主动巡护系统'
$env:RIVER_CAMERA_SOURCE = 'rtsp://用户名:密码@192.168.1.64:554/Streaming/Channels/102'
$env:RIVER_CAMERA_LOCATION = '河段 A'
$env:RIVER_CAMERA_INTERVAL = '8'
./run_rtsp.ps1
```

常见地址示例：

- 海康威视子码流：`rtsp://用户:密码@IP:554/Streaming/Channels/102`
- 大华子码流：`rtsp://用户:密码@IP:554/cam/realmonitor?channel=1&subtype=1`

实际路径以摄像头厂商文档为准。建议使用 720p 左右的子码流、5～15 FPS，并确保部署主机能访问摄像头的 554 端口。正式运行使用 `run_rtsp.ps1`，不要使用带 `--reload` 的开发启动命令。

## 演示顺序

1. 上传现场图片，模型检测到漂浮物并创建预警事件。
2. 填写处理人员，依次推进到“处理中”。
3. 填写漂浮物清理说明，推进到“已处理”。
4. 上传复核图片；模型未发现漂浮物后，复核通过。
5. 点击“确认复核通过”，再关闭并归档事件。

## 漂浮物数量预警规则

| 等级             | 判断条件      | 预警     | 建议                         |
| ---------------- | ------------- | -------- | ---------------------------- |
| 0 未发现漂浮物   | 0 个漂浮物    | 不预警   | 正常归档、定期巡查           |
| 1 少量漂浮物     | 1～3 个漂浮物 | 黄色预警 | 人工复核并安排巡查或清理     |
| 2 中等数量漂浮物 | 4～7 个漂浮物 | 橙色预警 | 安排现场清理并记录位置和数量 |
| 3 大量漂浮物     | ≥ 8 个漂浮物  | 红色预警 | 立即派单，防止继续聚集或扩散 |

置信度低于 0.3 的检测框会被模型过滤；通过过滤后，预警等级仅按识别出的漂浮物数量计算。

## 闭环状态

`待确认 → 已派单 → 处理中 → 已处理 → 复核通过 → 已关闭`

- 派单时必须填写处理人员。
- 标记“已处理”时必须填写漂浮物清理说明。
- 上传复核图片后，模型必须判定“未发现漂浮物”，才能复核通过并归档。

## 核心接口

| 方法  | 路径                        | 用途                                     |
| ----- | --------------------------- | ---------------------------------------- |
| GET   | `/health`                   | 检查服务、模型和数据库                   |
| POST  | `/predict`                  | 上传图片并返回漂浮物识别结果、预警和建议 |
| POST  | `/api/camera/frame`         | 分析浏览器摄像头抽取的一帧               |
| POST  | `/api/opencv-camera/start`  | 启动 USB、视频文件或 RTSP 视频源         |
| GET   | `/api/opencv-camera/stream` | 浏览器查看 OpenCV MJPEG 实时画面         |
| GET   | `/api/opencv-camera/latest` | 获取后台最近一次自动识别结果             |
| POST  | `/api/opencv-camera/stop`   | 停止 OpenCV 视频源和后台推理             |
| GET   | `/api/events`               | 查询事件台账                             |
| GET   | `/api/events/{id}`          | 查询事件详情和处理记录                   |
| PATCH | `/api/events/{id}/status`   | 推进事件状态                             |
| POST  | `/api/events/{id}/verify`   | 上传清理后的复核图片                     |

主要响应字段：

```json
{
  "floater_detected": true,
  "floater_level": 2,
  "floater_name": "中等数量漂浮物",
  "floater_count": 4,
  "confidence": 0.62,
  "location": "河段A",
  "warning_level": "橙色预警",
  "advice": "发现 4 至 7 个漂浮物，通知河道管理人员安排现场清理并记录位置和数量。",
  "event_no": "RIVER-20260723-0001"
}
```

旧的 `garbage_*` 和 `pollution_*` 字段暂时保留，用于兼容已有页面和调用方；新接入请使用 `floater_*` 字段。

运行数据保存在 SQLite 文件 `river_litter_mvp.db`，上传原图和检测框图片保存在 `static/uploads/`。不建议将运行数据库和上传文件提交到版本库。

## 项目结构

```text
app/          FastAPI 接口、推理、规则、数据库与摄像头服务
static/       管理页面及运行时上传的证据图片
tests/        接口、规则和摄像头自动化测试
weights/      YOLO 模型权重
data/         模型训练/验证配置
evaluation/   离线评估工具与清单
项目文档/      需求、设计和项目交付文档
```

本地环境变量可参考 `.env.example` 设置；临时文件、上传文件、缓存和本地数据库均已配置为忽略项。
